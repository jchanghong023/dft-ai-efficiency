# 场景使用指南

已经完成安装同步，接下来怎样用 OMP 做开发？从启动和一个简单任务开始，再按任务需要选择模型、计划或并发分工。本页只讲 OMP 与当前 fork 自带的日常能力；完整参数可查 [CLI 与 TUI](cli.html) 和[内置命令](commands.html)。尚未安装请先看[快速开始](quickstart.html)。

**先分清输入位置：** 标注“终端”的 `omp ...` 在 Linux Shell 中运行；标注“OMP 输入框”的 `/...` 和自然语言在启动后的 OMP 中输入。每个代码块是一次独立输入；示例项目路径、文件名、功能和模型名请换成自己的。

**常用操作优先按快捷键，fork 键位以 [fork.md](https://github.com/jchanghong023/oh-my-pi/blob/v18.1.10%2Bfork.172/docs-zh-CN/fork.md) 为准。** 下表在 OMP 主输入框中使用；按下组合键即可，不要把键名输入或粘贴进去。键位被个人配置修改、或终端拦截时，用 `/hotkeys` 查看当前绑定。

| 想做什么 | 默认快捷键 | 接下来怎么做 |
|---|---|---|
| 切换当前模型 | **Ctrl+T** | 输入模型名筛选，↑／↓ 选择，Enter 确认 |
| 配置 slow、Advisor 等模型角色 | **Alt+M** | 打开模型中心，选择角色与模型 |
| 在常用模型间轮换 | **Ctrl+P** | 按轮换列表切换，查看状态栏确认当前模型 |
| 切换 Plan 模式状态 | **Shift+Tab** | 依次开启、暂停、关闭；看状态栏确认 |
| 切换 Main／Discuss | **Ctrl+0** | 空闲时切换；讨论用 Discuss，实施切回 Main |
| 显示或隐藏思考内容 | **Alt+P** | 只改变 thinking blocks 的显示，不改变推理强度 |
| 调整推理强度 | **Alt+,**（Alt 加逗号） | 循环切换 thinking level，查看状态栏确认档位 |
| 查看 Agent 工作情况 | **Alt+A** | 打开 Agent Hub 查看任务和状态 |
| 展开工具调用详情 | **Ctrl+O** | 阅读执行输出；再次按下收起 |
| 打断当前执行 | **Esc** | 停止本轮，补充或纠正要求后继续 |

没有默认快捷键的操作仍使用斜杠命令，例如 Vibe、Advisor 开关、压缩和新会话。

## 1. 启动 OMP，或继续上次工作

**什么时候用：** 第一次在一个代码仓工作，或中断后继续之前的任务。

在**终端**进入目标代码仓再启动：

```bash
cd /path/to/your/project
omp
```

如果提示找不到 `omp`，在同一终端运行 `~/.local/bin/omp`，或按[快速开始](quickstart.html)设置当前 Shell 的 PATH。进入输入框后，先完成下一节的小任务。

要继续这个目录最近的会话，在**终端**运行：

```bash
omp -c
```

有多个历史任务，需要自己选择时运行：

```bash
omp -r
```

选中会话恢复后，先让 OMP 核对工作现场。在 **OMP 输入框**输入：

```text
先检查当前分支和未提交改动，结合上次记录告诉我做到哪里、
还有哪些步骤未完成，暂不修改文件。
```

确认恢复的是目标任务，再输入下一步要求。模型服务尚未配置或不可用时，进入[常用配置](config.html)中的模型接入步骤。

## 2. 简单任务，直接说清楚要求

**什么时候用：** 解释代码、局部小修改，或目标和验收条件都明确的任务。直接在 **OMP 输入框**输入自然语言即可。

只想理解代码：

```text
只读解释当前项目的命令行入口：
参数从哪里解析、如何调用主流程、出错时如何退出。
引用实际文件和函数，不修改代码。
```

要做一个小功能：

```text
给当前命令行工具增加 --version 参数，输出项目已有版本号后正常退出。
沿用现有参数解析方式，保留其他参数行为，补充相关测试并运行。
完成后说明改了什么和验证结果。
```

**下一步：** 阅读实际改动和测试结果；有遗漏就直接补充要求。如果 OMP 发现涉及多个模块或关键需求不明确，转到第 5 节先计划。

## 3. 切换模型，配置 slow 角色

**什么时候用：** 日常任务更换主模型，或为复杂推理准备一个更强的模型。

**切换当前模型：** 在 OMP 主输入框按 **Ctrl+T** → 输入模型名筛选 → 用 ↑／↓ 选中 → 按 Enter。查看状态栏确认模型已经改变，再提交任务。只想取消选择就按 Esc。

**配置 slow 角色：** 按 **Alt+M** 打开模型中心，选择需要的模型，按界面提示将它分配给 `slow` 角色并确认。`default` 用于默认主模型；`slow` 是供复杂任务调用的模型角色，不表示自动增加等待时间。为 `slow` 分配模型会保存角色配置，**不会立即把当前主模型换成它**。保存位置受模型角色的全局／项目设置控制。

配置好以后，要在当前会话用这个模型，按 **Ctrl+T** 选择刚才分配的模型即可。常用角色已加入轮换列表时，也可在主输入框按 **Ctrl+P** 轮换，看到目标模型后停止。

**下一步：** 复杂步骤完成后，再按 **Ctrl+T** 选回日常模型。模型列表为空时，先按[常用配置](config.html)接入模型服务。Ctrl+T 只切换本会话，Alt+M 中的角色分配则会保存配置。

快捷键不可用时，`/switch` 打开会话模型选择器，`/model` 打开模型中心。使用不带参数的入口即可，无需手输模型 ID 或角色别名。

## 4. 启用 Advisor，让第二模型检查过程

**什么时候用：** 希望开发过程中有另一个模型跟进主模型的工作，提示遗漏或问题。

先在 OMP 主输入框按 **Alt+M**，为 `advisor` 角色选择一个已接入的模型。基础用法采用这个角色作为第二模型；若本机已有多 Advisor 配置，以状态页列出的实际模型为准。

然后在 **OMP 输入框**启用：

```text
/advisor on
```

检查是否启动、使用哪个模型：

```text
/advisor status
```

**下一步：** 状态正常后照常输入开发任务，关注 Advisor 对主流程的建议。如果显示未配置或模型不可用，按 **Alt+M** 检查 `advisor` 角色；更详细的配置入口是 `/advisor configure`。不需要时关闭：

```text
/advisor off
```

Advisor 会产生额外模型调用；它提供检查和建议，不代替测试或用户审阅。`on`、`off` 控制本会话，不会持久化修改 `advisor.enabled`。

## 5. 新功能较复杂，先澄清再计划

**什么时候用：** 新功能涉及多个模块、接口或兼容性，或者还没想清楚具体需求。

在普通会话的 OMP 主输入框按 **Shift+Tab**，确认进入 Plan 模式，再输入需求：

```text
为当前工具增加批量处理功能。
先阅读现有单文件流程，向我澄清输入格式、失败处理、输出位置和兼容要求；
再给出实现步骤和测试验收方案，暂不实施代码修改。
```

**接下来按顺序操作：** 回答需求问题 → 阅读方案 → 补充遗漏 → 在计划审阅界面选择执行选项，开始实施。Plan 阶段先调查和形成方案，不直接修改项目代码。

计划审阅界面关闭后，仍在 Plan 模式时可重新打开：

```text
/plan-review
```

方案还不完整就继续提出修改意见；执行完成后核对测试和交付结果。**Shift+Tab 依次开启、暂停、关闭 Plan**；已有计划草稿时，离开规划还会要求确认。看到 `Plan ⏸` 表示暂停，要完全退出需再按一次并确认状态栏不再显示 Plan。切换模式不等于批准计划，开始实施使用计划审阅界面的执行选项。快捷键不可用时，可用 `/plan` 切换模式。需要多路分工时，在需求或计划中明确可独立的工作项，执行阶段采用第 7 节的并发方式。

## 6. Vibe 导演模式，持续指导多个 Worker

**什么时候用：** 你希望主会话负责安排和检查工作，让持续存在的 Worker 负责调查、编码和运行测试，并可以不断给它们补充要求。

先完成并退出 Plan 或 Goal 模式；**Vibe 与活动或暂停中的 Plan／Goal 都不能同时使用**。如果状态栏显示 `Plan ⏸`，再按一次 **Shift+Tab** 完全退出 Plan，然后在普通会话的 **OMP 输入框**输入：

```text
/vibe 按刚才确认的批量处理需求推进实现。
把参数入口和核心处理拆成边界清楚的工作流，
为各 Worker 说明负责范围、接口约束和验收要求；
独立工作并行，结果汇总后检查实际改动和测试。
```

主会话进入导演模式，负责调度和读取结果；Worker 执行搜索、修改和构建。内置 `fast` Worker 默认使用 `@smol`，`good` Worker 默认使用 `@task`；可按 **Alt+M** 提前配置这两个角色，不要把 `good` 默认模型误认为 `@slow`。

过程中直接在 **OMP 输入框**继续指导：

```text
补充要求：单个输入失败时继续处理其他输入，最终汇总失败清单。
请把这个约束传达给相关 Worker，并核对相应测试。
```

查看进展时输入：

```text
列出各 Worker 当前负责的任务、状态和阻塞项，
并区分已经验证的结果与尚未验证的结论。
```

**下一步：** 待 Worker 完成并检查结果后，再输入 `/vibe` 退出。退出会取消仍在进行的 Worker 轮次并结束该模式的 Worker 会话；它不是让 Worker 留在后台继续工作的开关。

## 7. 大任务分工并发，减少单个上下文负担

**什么时候用：** 一个任务含有多个可以独立调查或实施的工作项，全部放在主会话中容易累积大量细节。

在 **OMP 输入框**使用 `/orchestrate`，把任务边界写清楚：

```text
/orchestrate 按已经确认的批量处理方案实施。
先划分接口和文件边界，再把独立工作交给子代理并行完成：
一个负责参数入口，一个负责核心批处理，
一个只读检查边界用例和验收标准。
每个子代理接收完整需求、负责范围和交付要求，避免同时修改同一文件。
依赖前一步结果的工作按顺序推进，主会话整合后运行测试并总结。
```

子代理分别处理自己的上下文，主会话负责提供充分背景、协调接口和整合证据。无需手工调用 `task` 工具；可以让 OMP 按任务收益分配子代理。

如果明确追求最快完成，并接受不限制模型资源成本，在 **OMP 输入框**使用：

```text
/fullsend 完成已确认的批量处理功能并验证。
优先速度和经验证的质量，在独立工作上充分使用并发子代理，
依赖项按顺序推进，最后汇总实际改动和测试结果。
```

**下一步：** 按 **Alt+A** 打开 Agent Hub 查看工作情况；用 `/jobs` 可查询后台任务状态，也可直接要求汇总分工、阻塞项和验证结果。`/orchestrate` 强调多 Agent 编排；`/fullsend` 强调速度与验证质量，会按收益直接执行或委派，不保证开满并发，也不会自动修改并发上限。两者的提示效果受 `magicKeywords` 设置控制；复杂可编排工作流另见 [`/workflowz`](command-workflowz.html)。

## 8. 调整并发上限，或使用不设限模式

**什么时候用：** 已有足够多的独立任务，希望调整同时运行的子代理数量。

在**终端**查询并记下当前值：

```bash
omp config get task.maxConcurrency
```

需要提高到最多 16 个时运行：

```bash
omp config set task.maxConcurrency 16
```

需要允许尽可能多的独立子任务同时运行时，将上限设为 `0`：

```bash
omp config set task.maxConcurrency 0
```

`0` 表示不设限；它不是启动 0 个，也不是固定启动某个“最大数量”。该版默认值为 `8`。实际并发仍取决于任务能否拆分、模型服务限额和机器资源；提高上限也不保证任务更快。

**下一步：** 这些命令会持久化个人配置。设置后重新启动 OMP，再提交上一节的分工任务；也可在会话内用 `/settings` 的 Subagents → Max Concurrent Tasks 调整。若项目或启动覆盖层设置了同名值，需查询有效值并检查对应覆盖层。

任务结束后，如要恢复本次修改前的值，在**终端**将 `<原值>` 替换为刚才记下的数字：

```bash
omp config set task.maxConcurrency <原值>
```

仅当要恢复版本默认值时使用：

```bash
omp config reset task.maxConcurrency
```

## 9. 遇到问题，先诊断或直接修复

**什么时候用：** 程序报错、测试失败，或者想先知道根因而不修改代码。

在 **OMP 输入框**给出复现条件和真实报错。先只读诊断：

```text
/jchdiagnose 批量处理遇到一个无效输入后提前退出，其余输入没有执行。
请检查相关控制流和已有测试，定位根因并给出最小修复边界，暂不修改文件。
```

诊断结果确认后，要实施修复时输入：

```text
/jchfix 按刚才确认的根因修复批量处理提前退出的问题，
保留单文件模式原有行为，补充回归测试并运行相关检查。
```

修复完成后独立验证：

```text
/jchverify uncommitted
```

**下一步：** 按 **Ctrl+O** 展开工具执行输出，阅读验证证据；如果仍有失败，带着真实失败输出继续 `/jchfix`。`/jchverify` 验证当前未提交改动，不替你修复产品代码；测试可能生成临时输出。

如果异常发生在 **OMP 本身**，例如界面或模型请求异常，使用 `/debug` 打开调试入口；如果 OMP 找不到某个工具，使用 `/tools` 检查实际可见工具。它们与项目代码的根因诊断用途不同，进一步排查见 [FAQ / 最佳实践](faq.html)。

## 10. 生成单元测试，审查本次改动

**什么时候用：** 功能已经实现，需要补齐测试，或交付前想再检查功能问题。

直接在 **OMP 输入框**提出测试任务，无需先记住某个 Skill 名称：

```text
为当前项目的批量处理逻辑补充单元测试。
先查看已有测试框架和目录约定，覆盖空输入、单个输入失败后继续处理、
全部成功、全部失败及输出顺序。
使用现有依赖和测试风格，不修改产品代码。
运行相关测试，报告通过情况；发现实现问题时说明复现条件，不直接修复。
```

**下一步：** 核对测试是否真的执行、是否覆盖需求，而不只检查有没有新增文件。缺少运行环境或依赖时，让 OMP 说明未执行项；有产品缺陷则按上一节进入修复。

检查当前未提交改动中的功能问题，在 **OMP 输入框**输入：

```text
/jchfuncreview uncommitted
```

它进行只读功能审查；需要实际运行检查、收集交付证据时用 `/jchverify uncommitted`。审查与测试各提供一部分证据，可结合结果决定是否交付。团队预置的测试 Skill 操作另见[团队能力](team.html)。

## 11. 长任务：压缩、交接或重新开始

**什么时候用：** 对话很长、准备进入新阶段，或需要切换到一个无关任务。以下命令都在 **OMP 输入框**输入。

先查看上下文占用：

```text
/context
```

同一任务还要继续，但历史细节太多时，保留约束并压缩：

```text
/compact soft 保留批量处理的接口约定、失败处理规则、
已修改文件、测试结果和未完成事项。
```

阶段结束，想带着必要信息转入新会话时交接：

```text
/handoff 保留已确认方案、实现进度、关键文件、未通过的测试和下一步验收要求。
```

要开始完全无关的任务时：

```text
/new
```

**下一步：** 压缩或交接后先核对关键约束是否保留，再继续任务。`/new` 创建新会话，不会删除或回滚代码；要恢复之前的工作，使用 `/resume` 或在终端运行 `omp -r`。
