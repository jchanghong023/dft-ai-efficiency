# Test Point：改善可控性与可观测性

当 ATPG 长时间找不到模式，问题可能不是模式生成器“不够聪明”，而是某个内部节点很难被控制或很难把差异传到观察点。Test Point（测试点）是在满足功能约束的前提下增加测试专用控制/观察结构，让目标节点更容易被激活或观察。

## 两类基本测试点

- **控制点（control point）**：通过测试使能和额外控制值，帮助把内部节点推到需要的 0 或 1。它改善可控性，但可能增加逻辑、切换活动、面积和约束。
- **观察点（observe point）**：把内部节点或其组合结果接入扫描寄存器、观察链或其他测试通路，帮助把差异带到可读出的地方。它改善可观测性，也可能增加负载、布线和压缩/X 处理复杂度。

真实工具会根据候选位置、故障列表、时序、功耗和布局约束筛选点；不是节点越多越好。测试点还必须在功能模式下保持正确隔离，测试模式下的控制优先级、复位和时钟关系要经过 DFT DRC 与门级验证。

## 一个被掩蔽节点的故事

本页实验的 `h = a & b` 只在 `11` 时为 1，`p = a XOR b` 却在 `01/10` 时为 1；`out = h & p` 因此始终为 0。即使 `h` 或 `p` 的故障已经被激活，差异也可能被后级逻辑掩蔽。控制点把测试路径上的 `h` 强制为 1，观察点则直接捕获控制后的 `h`，分别解决激励和观察瓶颈。

## 怎样评价一个候选点

候选点不应只按“覆盖率增加多少”排序，至少要同时看：

1. 能改善哪些目标故障的控制或观察条件；
2. 是否增加时序路径、面积和布线负载；
3. shift/capture 功耗是否仍可接受；
4. 是否引入新的 X 来源、时钟/复位风险或模式约束；
5. 是否减少模式数和 ATPG 运行时间，且收益能在仿真与 ATE 上复现。

页面实验使用一个明确的布尔教学电路：`h = a & b`、`p = a XOR b`、`out = h & p`。四个输入模式全部枚举，故障集合固定为 `h stuck-at-0` 与 `p stuck-at-0`。由于 `h` 与 `p` 的取值组合，`out` 的差异会被掩蔽；实验逐模式比较好/坏电路，并列出实际被检出的故障和模式，不使用虚构的可控性分数或面积分数。

控制点在测试路径上把 `h` 强制为 1，扩大 `h` 故障的激励集合，也让 `p` 故障的差异到达 `out`；观察点直接捕获 `h`，绕过 `out` 的掩蔽。组合使用时，两条故障的检测集合都发生变化。这是一个可手算的逻辑模型，不是工具对真实网表的 coverage 预测。

## 控制点的实现注意事项

控制点通常需要测试使能、测试数据和功能数据的选择结构。测试使能的极性、复位值和默认值必须明确，避免功能模式误进入测试路径；组合逻辑还要检查新增多路选择器对时序和逻辑等价的影响。若控制点驱动高扇出网络，shift 与 capture 的翻转功耗也可能变化。

## 观察点的实现注意事项

观察点可能接到额外扫描单元、已有扫描寄存器或压缩观察网络。要确认观察路径的时钟、链长、压缩器连接和 X 屏蔽策略；否则“能看到”可能被压缩冲突或未知值抵消。新增寄存器也会影响物理布局、测试时间和模式协议。

控制点和观察点都要有可追踪的实例、原因、目标故障和验证结果。只在截图中标出一个节点，不能替代实现后的 DFT DRC、ATPG 和门级验证。

## 与 DFT 流程的关系

通常会先做 RTL 或网表级可测试性分析，再由工具提出或实现候选点，重新运行 DRC、ATPG、故障仿真、门级模式仿真和功耗/时序检查。测试点插入不应绕过功能验证，也不应把一个估算分数当作已完成的硅片质量结论。

如果目标是改善某一类故障，应先保留插入前基线：目标故障数、模式数、运行时间、shift/capture 功耗和关键路径。插入后对同一设计快照重新测量，才能把收益与代价归因于测试点，而不是归因于同时变化的约束或故障列表。

因此，测试点选择是一个可复核的工程决策，而不是动画中某个节点变亮就算完成。

## 常见误区

- **测试点不是修复功能逻辑**：它只在测试模式下提供额外的可控/可观测路径。
- **更多点不一定更好**：面积、时序、功耗、布线和模式复杂度可能反而恶化。
- **可控性与可观测性不是同一指标**：改善一个不保证改善另一个。
- **估算覆盖率不是最终覆盖率**：最终结果需要具体网表、故障模型、约束与仿真证据。
