# 团队公共能力

日常开发先记住一个入口：**`/code-and-verify <需求>`**。把要解决的问题、修改范围和预期行为写清楚，OMP 会先调查，再修改，最后验证。通常不需要记住 Agent 名称，也不需要手动编排它们。

## 怎么开始

完成[快速开始](quickstart.html)中的团队能力同步后，在目标代码仓启动 OMP，将下面的命令输入 OMP 对话框。它不是 Shell 命令。

```text
/code-and-verify <要完成的需求，以及必须保持不变的行为>
```

当前团队只有这一个自定义命令。它适合开发和缺陷修复，会在授权范围修改代码、补充并运行测试；不自动提交、推送或发布。只想读代码或解释概念时，直接向 OMP 提问即可。

## 可以用它做什么

### 修复一个已知缺陷

```text
/code-and-verify 修复 clamp(value, lower, upper) 在 lower > upper 时未抛出 ValueError 的问题。保留正常区间行为，使用项目已有 unittest 补充回归并运行。
```

OMP 会检查函数约定和已有测试，确定缺陷后最小修改，再用回归用例验证，而不是只给出修改建议。

### 完成一个范围明确的小功能

```text
/code-and-verify 为现有报告导出功能增加 CSV 格式，复用当前的数据筛选逻辑，不改变 JSON 导出行为；补充相关单元测试并执行已有检查。
```

写清楚要增加的行为和不能改变的部分，便于控制修改范围。测试沿用项目现有框架，不另建一套无关体系。

### 修改 RTL 并验证行为

```text
/code-and-verify 根据本工程的复位规范，修复 CORE_A 复位释放后首拍输出错误。保持模块接口不变，复用已有测试平台补充回归；仿真工具或库缺失时明确报告未验证项。
```

把规范位置、目标模块和现有验证入口一起提供更有效。没有仿真器或工艺库时，不会将静态检查说成仿真通过。

## 输入命令之后会发生什么

1. **调查**：读取相关规范、代码和已有测试，确认预期行为及修改边界。
2. **实现**：根据调查结果完成最小必要修改，保留其他已有改动。
3. **验证**：针对实际修改补充并运行相关测试；需要时执行项目已有集成测试。
4. **汇总**：说明改了什么、执行了什么、结果如何，还有哪些条件缺失。

简单任务可以由主会话直接完成。需要分工时，主会话通过 `task` 调用以下三个团队 Agent，并负责传递上下文与汇总结果。

| Agent | 做什么 | 为什么这样分工 |
|---|---|---|
| `document-worker` | 只读调查规范、代码和已有测试，返回文件位置、约束与缺口 | 先找到依据，避免实现建立在猜测上 |
| `coding-worker` | 接收调查结论，在指定范围完成最小代码修改 | 让实现围绕已确认的目标，不扩大修改范围 |
| `verification-worker` | 接收实际修改，补充并执行相关测试，返回真实结果 | 把“代码改了”和“行为验证过了”区分开 |

有依赖的阶段按 **调查 → 编码 → 验证** 推进，不让编码和验证在缺少前一步结果时并发猜测。并不是每次输入命令都会固定调用全部三个 Agent。

## 需要手动指定 Agent 吗

通常不需要。若只想做某一阶段，可以直接在 OMP 中说明用途，例如：

```text
请调用 document-worker，只读调查 CORE_A 的复位规范和已有测试入口，返回依据，不修改文件。
```

也可以在开发需求后补充“这次请按调查、编码、验证分工，依次调用三个团队 Agent”。由主会话使用 `task` 编排；Agent 名称不是独立的斜杠命令。

## 应该看到什么结果

结束时检查修改摘要、测试命令与结果、未验证项。仅有“已完成”一句话，不等于测试实际通过；测试失败或环境缺失应被明确说明。只有输入 `/code-and-verify` 而没有需求时，OMP 会先询问，不自行选择任务。
