故障模型与 ATPG

ATPG（Automatic Test Pattern Generation，自动测试图形生成）不是“把随机 0/1 塞进扫描链”。它从一个明确的故障模型出发，寻找能够激活故障、传播差异并在可观测点捕获的测试模式；随后还要经过故障仿真、时序/功耗约束和 ATE 格式转换。

本页实验为概念教学模型，不代表真实工具实现、时序签核或插入验证结果。

先区分缺陷、故障模型与测试模式

  • 物理缺陷是制造过程中的开路、短路、参数偏差等真实原因。
  • 故障模型是为了可计算而对缺陷的抽象，例如某个节点永久为 0 的 stuck-at-0。
  • 测试模式是施加到输入、扫描寄存器、时钟和模式控制上的一组时序值。
  • 检测意味着无故障模型与有故障模型在某个观测点产生可区分的响应，不等于已经定位物理缺陷。

同一物理缺陷可能需要多个模型近似；一个模型被检测，也不表示所有相关缺陷都被检测。工具版本、库模型、约束和故障折叠规则都会影响故障列表。

常见模型

模型 抽象 适合说明什么 边界
stuck-at-0/1 节点恒为固定值 逻辑值被永久拉低/拉高 不描述延迟或电气强度
transition rise/fall 0→1 或 1→0 的转换受阻 速度相关的时序缺陷 需要 launch/capture 与时钟约束
bridging 两个网络发生耦合 短路/桥接的逻辑后果 具体行为取决于桥接模型与驱动关系
path-delay 一条路径的延迟超限 路径级时序缺陷 需要时序数据，不能只看静态逻辑
cell-aware 单元内部缺陷的模型 标准单元内部开短路等 依赖库/版图与专用模型

ATPG 的四个问题

  1. 能否控制：把起点输入或扫描寄存器设成需要的值。
  2. 能否激活：让好电路在故障位置产生与故障值不同的值。
  3. 能否传播：沿逻辑路径把差异传到输出、扫描捕获寄存器或压缩器。
  4. 能否观察：在合法的 capture/shift 协议下读出差异。

下面的小实验把这四步拆开显示。它是一个固定的教学组合电路，不是某个工艺库或 ATPG 工具的替代品。

读懂实验结果

“未检测到”至少有两种含义：本次模式没有激活/传播该故障，或者故障在当前约束下不可测试。工具报告通常还会区分 aborted、untestable、possibly-detected 和因 X 值造成的未知结果；不能把它们都简单当作“通过”。

实验选择的是单个模式和单个故障，按钮显示的 detected 只表示本例的输出可区分。真实 ATPG 还要生成模式集合，进行全故障列表仿真，并检查扫描规则、时钟、复位、X 处理、功耗和测试时间。

常见误区

  • 随机模式多，不等于覆盖率高：难测故障可能需要特定控制/观察条件。
  • 测试模式能跑，不等于硅片一定能测：ATE 时序、电压、负载、IR drop 和噪声仍需验证。
  • stuck-at 覆盖率高，不等于 transition 覆盖率高：二者的激励和捕获时序不同。
  • 一个 failing pattern 不等于故障定位完成：诊断需要多模式响应、候选故障分析和物理证据。

工程上如何读一条失败记录

先记录故障模型和实例路径，再确认模式是否满足测试协议；随后分别检查故障点的好/坏值、差异传播路径和最终 capture 位。若中间出现 X，应区分“未知掩盖了差异”和“逻辑上没有差异”。修复 DFT 约束后，必须重新生成或重新仿真模式，不应手工改一位后继续使用旧模式。

对于 transition 故障，还要把 launch、capture 时钟沿、周期时间和时钟门控记录下来。只在低速 shift 阶段看到 0/1 正确，不能证明高速 capture 没有延迟故障。

本实验的边界

实验固定了一个两输入组合电路和一个简化桥接模型；没有模拟扫描寄存器、X、时序延迟、功耗、约束传播或 ATE 电气条件。它展示“激活 → 传播 → 观察”的推理顺序，不能输出真实模式文件、覆盖率或 Sailor/商业工具插入结果。

公开参考
