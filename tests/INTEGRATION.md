# 团队公共能力集成测试指南

本文供执行测试的 Agent 使用，不是自动测试脚本。阅读本文不代表测试已经执行。

## 1. 测试范围与硬性限制

只测试以下六项能力的真实行为：

- `document-worker`：只读调查。
- `coding-worker`：按范围修改代码。
- `verification-worker`：补充并运行相关测试。
- `/code-and-verify`：自定义开发与验证命令。
- `generate-unit-tests`：单元测试 Skill。
- `generate-dft-circuit`：基础电路生成 Skill。

使用当前系统 PATH 中已经安装的 `omp`，记录解析出的实际路径和版本。不得使用本仓库 `dist/` 的二进制，不下载、升级或替换 OMP，不执行打包测试，也不运行 `scripts/sync.py`。

**唯一允许的模型：**

| 项目 | 固定值 |
|---|---|
| Provider | `opencode-zen` |
| Model ID | `muse-spark-1.2-contributor-free` |
| 完整选择器 | `opencode-zen/muse-spark-1.2-contributor-free` |

主会话、三个子代理及任何辅助模型调用都必须使用上述模型。不得使用默认模型、模糊匹配、其他免费模型、付费模型或备用提供方。模型名称含 `free` 不等于已经验证当前服务可用。

**默认配置下无法使用该模型，就报告并停止整个集成测试。** 包括模型未注册、缺认证、服务拒绝、限流、超时、无响应、工具调用不支持，或无法确认实际使用的模型。不得为继续测试注册账号、购买额度、添加虚假密钥、更换模型或自动重试。过程中出现同类问题也立即停止，剩余用例标记为未执行。

## 2. 开始前准备

### 2.1 确认安装入口与调用方式

先只读查询，不发送模型请求：

- PowerShell：`Get-Command omp -All`，确认实际执行项与目标路径。
- Linux：`command -v omp`，确认软链接的最终目标。
- 使用该入口读取 `omp --version`、`omp --help`，核对当前安装版支持的模型选择、项目目录、配置覆盖与会话记录方式。

如果入口最终指向本仓库 `dist/`，或系统中没有 OMP，报告前提不满足并停止。Windows 与 WSL 是不同安装环境，不因一边不可用就悄悄切换另一边。

本文的发现目录与调用示例参考 `.tmp/omp-reference/` 中的 Fork 源码；实际执行必须以系统安装版的帮助、工具 schema 和配置机制为准。不能把手册参考版本当作安装版本，不能猜测不支持的参数。

### 2.2 准备隔离项目与能力文件

在本仓库 `.tmp/team-integration/<运行标识>/` 下保存普通代码用例、配置覆盖、会话记录和报告。不要使用真实业务代码或公司文档；不要覆盖个人 `~/.omp/agent/`。

按当前安装版的项目级发现机制，将以下文件原样复制到各测试项目：

| 仓库源文件 | 项目内目标 |
|---|---|
| `omp/AGENTS.md` | `.omp/AGENTS.md` |
| `omp/agents/*.md` | `.omp/agents/` |
| `omp/commands/code-and-verify.md` | `.omp/commands/code-and-verify.md` |
| `omp/skills/generate-unit-tests/` | `.omp/skills/generate-unit-tests/` |
| `omp/skills/generate-dft-circuit/` | `.omp/skills/generate-dft-circuit/`，包括 `references/` |

每个独立用例使用干净的夹具副本和新会话，避免前一个用例的修改或上下文代替当前能力。记录源文件校验值与实际发现来源，排除个人同名定义覆盖。不要把能力正文粘进提示词来模拟加载，不修改被测定义来让测试通过。

电路生成用例另使用**本仓库以外**明确指定的可丢弃工程，例如外部工作区的 `.tmp/team-integration/<运行标识>/circuit/`。没有合适的外部目标就将该用例记为受阻；不要在效率仓库创建 tiny_base 工程。报告和必要日志仍放本仓库 `.tmp/`，不复制公司库资料。

### 2.3 锁定免费模型，再探测一次

使用一次性、仅作用于本轮的配置，不修改个人持久模型配置：

1. 读取安装版提供的模型清单与有效配置，确认精确 provider/model 存在且为免费入口。
2. 用完整选择器固定主模型；将子代理模型及实际可能触发的角色也固定为同一模型。禁用自动模型切换、付费辅助调用和所有 fallback 链。`--models` 通常只是模型轮换列表，不能当作禁用 fallback 的保证。
3. 检查配置合并后的有效值；仅靠提示词说“不要用其他模型”不足以满足限制。无法在请求前确认约束有效时，停止，不试运行。
4. 发送一次最小只读请求，例如“只回复 `TEAM_INTEGRATION_READY`，不调用工具”。记录实际 provider/model、退出状态与服务响应，不记录密钥。
5. 请求成功且实际模型精确一致，才开始六项能力测试。仅出现在模型清单里不能算可用。

若安装版支持，启动形态为 `omp --model opencode-zen/muse-spark-1.2-contributor-free --cwd <用例绝对路径> --config <本轮覆盖文件>`。先按实际帮助验证占位参数及覆盖配置语法，再执行；这条命令本身并不证明子代理和 fallback 已受限制。

自定义命令和显式 Skill 调用优先从 OMP 输入框提交。若使用非交互模式，先核实该版会展开斜杠命令，而不是将其作为普通聊天文字。每次子代理启动都检查实际模型；发现偏离就立即中止本轮，不继续产生请求。

## 3. 最小代码夹具

由执行测试的 Agent 预先创建一个 Python 3.11+ 小项目，只使用标准库 `unittest`，不安装依赖：

- `SPEC.md`：规定 `clamp(value, lower, upper)` 将数值限制在闭区间；区间内返回原值；`lower > upper` 必须抛出 `ValueError`。
- `clamp.py`：故意缺少非法区间检查，其余行为正确。
- `tests/test_clamp.py`：已有正常区间内测试，但缺少非法区间回归。
- `KEEP.txt`：用户已有内容，所有能力必须保留。
- 已有测试入口：用已确认的 Python 3.11+ 运行 `-B -m unittest discover -s tests -v`。

将夹具初始内容与已有测试入口记录在运行目录；需要 diff 时可以在夹具内初始化本地 Git 基线，不提交本仓库。临时 Git 身份仅限夹具本地。实际运行前后检查文件变化，不能仅凭 Agent 的总结判断通过。

## 4. 六项能力用例

### A. document-worker：只读调查

对主会话说：

> 必须通过 task 调用 document-worker，只读调查本项目 clamp 的规范、实现差异和已有测试入口。没有 Wiki 数据库时读取 SPEC.md，不创建索引。返回文件位置和缺陷依据，不修改任何文件。你不要代替子代理完成调查。

通过条件：存在真实 `task` 调用及该子代理完成记录；准确指出非法区间缺少 `ValueError`；引用真实文件位置和已有测试入口；未改动项目文件、未创建数据库、未执行状态变更命令。

检查子会话工具记录，而不只检查主会话转述。主会话自行回答、只列出 Agent 名称或只创建任务未等待完成，都不通过。

### B. coding-worker：最小实现

使用新夹具，向主会话提供 A 的已确认依据：

> 必须通过 task 调用 coding-worker。依据 SPEC.md，仅修复 clamp.py 对 lower > upper 未抛出 ValueError 的问题，保持其他行为及 KEEP.txt 不变，不修改测试、不升级依赖。返回实际修改与验证入口。你不要代写代码。

通过条件：真实子代理完成；产品 diff 仅包含必要修复；正常行为保持；`KEEP.txt` 和测试不变。执行测试的 Agent 独立运行已有测试，并检查非法区间是否抛出异常，不能仅接受“已修复”的文字。

### C. verification-worker：测试与失败识别

使用含 B 修复的新副本，保留可见的修复 diff：

> 必须通过 task 调用 verification-worker。依据实际 diff，复用 unittest 补充非法区间回归和相关上下界用例，执行现有测试入口。只改测试及必要 fixture，不修改 clamp.py 或 KEEP.txt，报告命令、退出码、结果和未验证项。

通过条件：真实子代理完成；新增测试覆盖修改行为；确实运行并等待测试结束；日志与报告一致；产品代码未变。

再在另一副本中保留新增测试、恢复缺陷版本，让该 Worker 运行同一入口。应报告断言/异常预期失败，给出可复现证据，不改产品代码、不删用例或降低断言。此用例中“正确报告失败”才是通过。

### D. /code-and-verify：真实命令展开

在新夹具的 OMP 输入框输入：

```text
/code-and-verify 修复本项目 clamp 对非法区间未抛出 ValueError 的问题；依据 SPEC.md，补充相关 unittest 并运行已有入口，保留 KEEP.txt，不提交。
```

通过条件：命令来自本轮复制的文件，实际参数完成展开；调查规范与已有测试后完成最小修复、补充并执行回归；独立检查修改和测试结果。简单需求允许主会话直接完成，**不要求该命令强制启动三个 Worker**，Worker 行为由 A—C 单独证明。

另开新会话只输入 `/code-and-verify`：应询问需求，不自行修改项目。未识别命令、把命令当普通文字，或只有测试计划却未执行，都不能算主用例通过。

### E. generate-unit-tests：显式与自动选择

准备已修复 `clamp.py`、保留真实 diff、尚未补充回归的两个独立副本。

显式调用：

```text
/skill:generate-unit-tests 针对 clamp.py 的实际修复补充回归，复用本项目 unittest 并执行已有测试入口，不修改产品代码。
```

自动选择用例使用新会话，不提 Skill 名称：

> 请根据本项目 clamp.py 的实际修改，在已有测试框架中补充相关单元测试并执行，保留产品代码不变。

两次分别记录 Skill 加载/展开证据、测试 diff、命令与退出码。应使用已有 unittest，覆盖回归与相关边界，不另建框架、不改产品代码。仅产出相似测试但没有 Skill 加载证据，不算 Skill 集成通过；自动选择未发生须如实记录，不能事后手动加载冒充自动选择成功。

### F. generate-dft-circuit：基础生成与缺少资料

使用外部隔离工程，明确没有 PAD 库与 Sailor 资料。显式调用：

```text
/skill:generate-dft-circuit 在当前指定的外部测试工程生成 DFT 插入前基础 RTL，采用默认 TOP → CORE_A → CORE_B 层级和 tiny-base.md 接口；功能复位采用同步低有效。提供文件清单、测试平台和 Python 3.11+ 验证入口。当前没有 PAD 库和 Sailor 资料，不加入后续 DFT 结构。
```

在另一个干净外部工程、新会话中用同样需求但去掉 `/skill:generate-dft-circuit`，检查自动选择与真实加载证据。

分别检查：

- 读取 Skill 及 `references/tiny-base.md`；实际文件在指定外部工程，未写回效率仓库。
- 层级、接口、复位和普通 DFF/组合逻辑符合参考规范；无未要求的 Scan、EDT、Wrapper、IJTAG、TAP、Boundary Cell 或 OCC 实现。预留端口名称不等于已插入相应结构。
- 缺少 PAD 库时明确标注“未接真实 PAD”，列出单元、端口和模型缺口；不伪造工艺单元，不报告完成真实 PAD 接入。
- 文件清单与生成模块一致；测试平台包含可观察行为断言。已有 HDL 仿真器时实际运行；未安装则明确标记仿真未执行，不安装新工具、不用静态检查冒充仿真。
- Python 入口真实调用现有工具或明确报告缺失，不无条件打印成功。

最后在显式用例会话追加：“继续做真实 EDT 插入，但仍没有 Sailor 文档和 PAD 库。”应指出资料缺口，保留现有基础设计，不编造 Sailor 命令、假 EDT 或插入成功结果。**准确报告条件缺失是本负向用例的预期结果**，不要求完成真实插入。

## 5. 优先用 /dump 定位问题

每个用例完成后，以及命令未展开、Skill 未加载、Worker 未执行或结果异常时，优先在**对应 OMP 会话输入框**执行内置 `/dump`。先保存现场，再分析；不要先重试、切换模型或修改能力文件。

参考源码中，`/dump` 将格式化会话复制到剪贴板，包含系统提示、当前模型配置、工具清单、消息及工具调用/结果；还会尝试写出 LLM request JSON，并提示实际文件路径。它不是 Shell 的 `omp dump`，也不应假设支持 `/dump <文件路径>`。执行时以安装版实际反馈为准。

操作与排查顺序：

1. 将本次 `/dump` 产生的剪贴板内容保存为运行目录下的 `<用例>-session-dump.md`；确认复制成功，不能将旧剪贴板内容当成当前证据。若产生 JSON 附件，记录提示的真实路径并将必要调试副本归入本轮 `.tmp/`，不猜文件名。
2. 查 `Configuration` 的 provider/model、有效工具和系统上下文，确认本轮能力是否可见。该模型字段是当前配置快照，不单独证明此前所有请求、子代理都用了同一个模型。
3. 查用户消息和实际上下文：`/code-and-verify` 是否展开且带入需求；显式 Skill 是否展开；自动 Skill 是否有真实加载记录，而非模型只提到了名称。
4. 查 `Tool Call` / `Tool Result`：是否调用正确 Worker、传入正确需求，是否收到完成结果；读取、修改和测试执行发生在哪个文件、返回了什么错误。
5. 主会话 dump 不一定包含子代理完整过程。沿实际 task 返回的会话/产物引用查看对应子会话记录；安装版支持进入子会话时，在其中再 `/dump`。不要把主会话的一句汇总当成子代理执行证据。
6. 将首个有意义的错误、相关调用、文件 diff 和测试退出码对照，区分发现/展开问题、模型服务问题、工具执行问题、实现或测试断言失败。引用必要片段和日志位置，不在报告粘贴整份 dump。

`/dump` 的 JSON 附件可能包含原始上下文或敏感内容，只留本地调试；报告引用前检查并脱敏，不提交到 Git。若剪贴板不可用、无消息可导出或附件导出失败，记录具体情况，使用已有会话日志；不得声称已经拿到 dump。请求 JSON 是调试快照，不自动等于已成功发送或服务端已接受的请求。

模型不可用时仍可对已有失败现场做本地 `/dump`，但不得再发送模型请求；这不改变“报告并停止”的规则。

源码依据（只读参考，安装版可能不同）：`.tmp/omp-reference/packages/coding-agent/src/modes/controllers/command-controller.ts` 的 `handleDumpCommand()`，以及 `src/session/session-dump-format.ts`。
